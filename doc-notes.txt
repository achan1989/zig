Manually navigating to localhost#std.io.AnyReader does return the correct docs.
Look at JS in more detail around page loading.

When URI #fragment changes, call onHashChange() -> navigate() -> updateCurNav().
updateCurNav() takes the fragment part and calls e.g. findDecl("std.io.Reader").
Then sets curNav.decl = findDecl(), which just wraps wasm_exports.find_decl()
This does Decl.find() as the preferred result. If this doesn't find anything, it falls back to comparing the search string to every decl's FQN.
For URL#std.io.Reader the preferred Decl.find() yields a result.
For URL#std.io.AnyReader the preferred Decl.find() yields a result.

Decl.find() walks each component (e.g. `std` then `io` then `Reader`), resolving aliases at each step.


So it seems that the JS is doing unnecessary and ultimately harmful work.
When rendering the std.io namespace page, it resolves std.io.AnyReader to an aliasee that is ambiguous.
And whenever we navigate to a specific decl, the JS calls wasm_exports.find_decl(), which also resolves aliases.
So what if we skip the alias resolution in JS? Just link to the fqn of the alias, not the aliasee.
